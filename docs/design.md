# cycle-skill 설계

> 이 문서는 cycle-skill이 왜 이렇게 생겼는지를 적는다. 쓰는 법은 `README.md`, 각 단계의 절차는 `skills/*/SKILL.md`가 정본이다. 셋은 서로를 다시 쓰지 않는다.

---

## 0. 왜 다시 세우나

1.x를 회사 프로젝트에 여러 사이클 돌린 뒤 남은 관찰이다.

1. **1.x는 핸드오프 기계였다.** scope는 plan 세션에, design은 Sonnet에, do.md는 close 세션에 넘기려고 존재했다. 모델을 통일하고 세션을 안 바꾸면 경계가 없고, 문서 다섯 장의 존재 이유가 사라진다.
2. **세션 분리가 캐시에 거꾸로였다.** 단계마다 새 세션 = 매번 콜드 캐시. 한 세션이 캐시 친화적이다. 배치의 역할은 "캐시 대비"가 아니라 컴팩션 · 세션 단절 뒤의 **복구 지점**이다.
3. **계획을 잠근 자물쇠가 짠 사람을 막았다.** plan · design 읽기 전용은 Sonnet이 설계를 멋대로 바꾸는 걸 막으려던 장치다. 짠 놈과 하는 놈이 같은 세션이면 구현 중 수정마다 질문으로 멈추는 것만 남는다.
4. **"뭘 바꿨나"는 30장인데 "지금 어떻게 동작하나"는 0장이었다.** 현재 규칙이 이슈 본문과 닫힌 사이클 문서에 흩어져 있어 세션마다 코드를 다시 뒤졌다.
5. **close가 이슈를 만들어 백로그를 불렸다.** 사이클 하나가 발견 5개를 이슈로 만들고 2개를 처리하면 순증 +3이다. 방금 만든 이슈가 다음 사이클을 차지했다.
6. **고르는 일이 사이클 안에 있었다.** propose는 백로그 전체를 보고 골라야 하는데, 고르기는 사이클 단위가 아니라 주간 단위의 일이다.

## 1. 계약 — 비서 ↔ cycle

고르기는 사이클 밖(업무 스케줄링 비서)이 한다. cycle은 **"한다"만** 한다.

```
IN : 이슈 번호 n개
OUT: 닫힌 이슈 · 이월 이슈 · 발견 목록 · 태그 · 미실증(RISKS)
```

cycle은 이슈를 고르지도 만들지도 않는다. 발견은 결과 절의 표로만 남기고, 승격은 비서(사용자)가 정한다. 예외는 릴리즈된 것을 깨는 버그 하나 — 즉시 이슈.

## 2. 원칙

| # | 원칙 | 뜻 |
|---|---|---|
| P1 | 정본은 git, 백로그는 GitHub Issues | 사이클 문서는 레포에 있다. 백로그 · 마일스톤 · 릴리즈는 GitHub이 맡고 스킬은 `gh`로만 만진다. 자체 서버 · 설정 파일 · 토큰 파일은 없다 |
| P2 | 문서는 독자로 정의한다 | 절마다 독자가 있고 상한이 있다. 독자 없는 절은 없앤다. 같은 독자에게 같은 내용을 두 곳에 쓰지 않는다. README도 예외가 아니다 |
| P3 | 검증은 배치가 한다 | 배치 범위만. 전체 검증은 close가 한 번. 수단을 낮추지 않는다. 미실증 종류는 사용자만 정한다 |
| P4 | **사이클 하나 = 세션 하나** | Opus 한 세션으로 start부터 close까지. 끊기면 resume. 서브에이전트 없음 |
| P5 | 의식적 형식 금지 | 고정 개수 선택지, 합산 수치, 개정마다 자라는 요약, 통과를 선언하기 위한 게이트 표, 감사를 위한 감사를 두지 않는다. 전제조건은 조용히 확인하고 막힐 때만 말한다 |
| P6 | 판단은 사용자 | 범위 · 미실증 · 폐기 · 발견 승격 |
| P7 | 산출물에서 사용자는 "사용자" | 이름 · 호칭 · 대화체를 쓰지 않는다. 사용자의 말을 원문 그대로 인용하지 않고 감싼다("사용자가 만족했다") |
| P8 | README는 사용법까지만 | 표준 양식이 있고 close가 사이클마다 대조한다. 상태 · 이력 · 버전 · 개수 · 설계 근거는 README에 쓰지 않는다 |
| P9 | **배치 = 체크포인트** | 배치 끝 = 커밋 `B-n: {이름}` + 문서 배치 행 갱신. 이 둘만으로 어디서든 이어간다 |
| P10 | **계획은 계약이 아니라 가설** | 배치 · 결정은 세션이 고치고 기록만 남긴다. 순서 바꾸기 · 쪼개기 · 합치기 · 파일 · 검증 수단 전부. 범위(무엇을 왜)만 사용자 합의 |

**사용자에게 묻는 경우 — 닫힌 목록.** 이 셋 외에는 묻지 않는다.

1. 범위 절의 "무엇을 왜"가 바뀐다(항목 빼기 · 새 항목 · 합의한 동작과 다르게 만들기)
2. 검증 수단대로 볼 수 없다(미실증 종류 결정)
3. `docs/SPEC.md`에 적힌 동작을 바꾼다

판단 기준 한 줄: 사용자가 close 때 결과를 보고 "이거 내가 합의한 거 아닌데?" 할 수 있는가. 그럴 수 있으면 질문, 아니면 고치고 결정 행.

## 3. 흐름

```
/cycle:start #52 #89 #84
   이슈 읽기 → 항목별 "구체적으로 무엇을 하나" 합의 → 문서 골격(범위 · 배치) · 마일스톤 · 브랜치 → B-1 착수
   B-n: 구현 → 배치 검증 → 커밋 → 배치 행 갱신 → "다음"
/cycle:resume
   범위 절 + 미완 배치 행 + git log만 읽고 다음 미완 배치부터. 문서 전체를 읽지 않는다
/cycle:close
   전체 검증 1회 → 결과 절 → SPEC 흡수 → RISKS → README 대조 → 머지 · 태그 → 이슈 닫기 · 이월 → 마일스톤 닫기
/cycle:release
   배포를 결정했을 때. 사이클과 무관
init · scaffold
   사이클 밖 유틸
```

do는 스킬이 아니다. "다음"이 프롬프트다. `--auto` 없음.

start의 합의는 1.x propose의 "항목별 풀어 쓰기"를 잇는다. 이슈 본문은 추상화돼 있어 그대로 배치로 자르면 오해가 난다.

### 3.1 release

사이클과 무관하게 **배포를 결정했을 때** 부른다.

| 대상 | GitHub Release | 용도 |
|---|---|---|
| `develop` | pre-release | 대내. 보고 · 검수 · 게시 |
| `main` | release | 대외 |

노트는 **직전 같은 종류 릴리즈부터 대상 태그까지의 diff**로 쓴다. 사이클 문서를 모으지 않는다. 사이클 밖에서 커밋한 것도 diff에 있으므로 빠지지 않는다. `main`은 태그로 `--ff-only` 전진한다(룰셋으로 막혀 있으면 `## cycle` 절에 적힌 방식). 릴리즈 노트 파일을 레포에 남기지 않는다. GitHub Release 본문이 정본이다.

### 3.2 작은 수정

패치 트랙은 없다. 설계가 필요 없는 수정은 통합 브랜치에 그냥 커밋한다. 이슈에서 나온 것이면 커밋 메시지에 `closes #n`. 급하면 태그를 찍고 release를 부른다. 설계가 필요하면 그것은 사이클이다.

## 4. 문서

### 4.1 사이클 문서 — 한 장

`docs/cycles/v{N}/{버전}-{이름}.md`

| 절 | 독자 | 쓰는 이 | 상한 | 바꾸는 이 |
|---|---|---|---|---|
| 범위 | resume · 사용자(이해용) | start | 항목당 3줄 + "왜 이렇게" 1~2줄 | **사용자 합의** |
| 배치 | resume · close | start가 목록, 배치마다 상태 · 검증 결과 갱신 | 배치당 표 1행 + 메모 1줄 | 세션 |
| 결정 | close | 배치 중 | 행당 2줄, 현재값만 | 세션 |
| 결과 | 비서 · 마일스톤 | close | SC당 1줄 · 발견 표 · 다음에 바꿀 것 3줄 | close |

- 회차 R-n 없음. 이력은 git log.
- report 없음. 결과 절을 close가 마일스톤 설명에 덧붙인다(마일스톤에는 코멘트가 없다).
- 질문 절 없음. 묻는 건 대화로, 답만 결정 행에.
- 상한은 깔끔함이 아니라 **resume 비용**이다. 문서가 크면 컴팩션 뒤 다시 읽는 값이 커진다.
- 한국어. 사용자는 "사용자". 헤더는 표 하나(`사이클 · 버전 · 상태 · 시작 · 갱신`), 값은 교체한다. Version History · 요약 절 · 합산 수치 · 마크다운 링크를 두지 않는다. 파일은 경로를 인라인 코드로, 이슈는 `#n`으로 가리킨다.
- 파일 이름 `{버전}-{이름}.md`. 버전이 열쇠고 이름은 꼬리표라 겹쳐도 된다. 메이저 폴더 `v{N}`. 인덱스 파일은 없다. `ls docs/cycles/v*/`가 인덱스다. 브랜치 이름은 파일 이름(확장자 제외)과 같다.

### 4.2 프로젝트 수명 문서

| 문서 | 답하는 질문 | 쓰는 이 |
|---|---|---|
| `docs/SPEC.md` | 지금 이 시스템이 어떻게 동작하나 — 국면별 규칙과 수치, 불변식 | close가 흡수. **처음 흡수할 규칙이 생길 때 만든다.** 빈 파일을 먼저 만들지 않는다 |
| `docs/cycles/RISKS.md` | 무엇을 안 보고 나갔나 | close가 더한다(§4.3) |

SPEC은 설계 문서(왜)도 기획서도 README도 아니다. 규칙과 수치만. 국면당 10줄 상한. start가 코드를 뒤지기 전에 읽는다. SPEC에 적힌 동작을 바꾸는 건 범위 변경이다(§2 묻는 경우 3).

### 4.3 미실증과 리스크 장부

SC를 수단대로 볼 수 없는 일이 생긴다. 실제 사건 유발, 동시 세션 여러 개, 별도 브라우저 프로필, 긴 대기.

**백로그가 아니다.** 백로그는 아직 안 만든 것의 후보다 — 고를 수 있고, 미뤄도 되고, 하면 는다. 미실증은 셋 다 아니다. 이미 만든 것이 되는지 모르는 채 나가는 일이고, 미루는 동안 그 코드는 릴리즈에 계속 실린다. 이슈로 만들면 `p3`를 달고 새 기능과 나란히 서서 영원히 안 골라지고, 안 끝난 사이클이 끝난 것처럼 도장이 찍힌다.

| 상황 | 자리 |
|---|---|
| 수단대로 봤다 | 배치 `완료` · 결과 `됐다` |
| 수단대로 못 봤고 사용자가 종류를 정했다 | 배치 `미실증` · 결과 `미실증(종류)` · **장부** `docs/cycles/RISKS.md` |
| 수단대로 못 봤고 사용자가 정하지 않았다 | 검증 안 된 배치. close가 막힌다 |

- 배치는 수단을 **낮추지 않는다**(수치 대조 → 정성 판정). 못 보면 질문이고, 종류는 사용자만 정한다 — `재현 불가`(조건이 갖춰지면 볼 수 있다) · `검증 안 함`(보지 않기로 정했다).
- 장부는 레포에 하나. `버전 · SC · 검증되지 않은 것 · 종류 · 사유 · 해소`. **행을 지우지 않는다.** 나중에 본 사이클이 해소 열에 버전을 적는다. 어느 버전이 무엇을 안 본 채 나갔는지가 이력이다.
- start는 장부의 미해소 행 중 이번 범위와 같은 화면 · 같은 조건에서 볼 수 있는 것이 있으면 붙이자고 한 줄 제안한다. 고르는 대상이 아니라 묻어가는 것이다.

## 5. 배치

- 하나 구현 · 검증 · 커밋 · 문서 1행. 그 뒤 다음.
- 검증은 배치 범위만. 전체는 close 1회.
- 미실증 · 수단 낮추지 않기 · 배치 밖 skip으로 초록 만들지 않기.
- 플레이스홀더 · TODO를 남기고 다음 배치로 가지 않는다.
- 배치를 고치는 건 자유다. 고쳤으면 결정 행 하나.

검증은 세 겹이 될 수 있다. 각각의 자리를 정한다.

| 겹 | 자리 | 범위 | 스킬의 태도 |
|---|---|---|---|
| 배치 검증 | 배치마다 | 그 배치가 건드린 범위 | 돌리고 기록한다 |
| 전체 검증 | close, 사이클에 한 번 | `## cycle` 절의 전체 명령 | 머지 전 게이트. 돌리고 기록한다 |
| 원격 CI | GitHub Actions 등, 통합 · 릴리즈 브랜치 푸시 | 프로젝트 설정 | **기다리지 않고 기록하지 않는다.** 안전망이다 |

원격 CI는 통합 · 릴리즈 브랜치 푸시에 걸린 것으로 본다. 사이클 브랜치에도 걸려 있으면 배치 커밋을 푸시할 때마다 돌게 되므로 init이 빼기를 권한다.

## 6. 백로그 · 브랜치 · README · CLAUDE.md

### 6.1 백로그 = GitHub Issues

| 개념 | GitHub |
|---|---|
| 항목 | 이슈 |
| 우선순위 | 라벨 `p1` `p2` `p3` |
| 대기 | 열림, 마일스톤 없음 |
| 진행 | 열림, 마일스톤 배정 |
| 보류 | 라벨 `hold` + 착수 조건 코멘트 |
| 완료 | 닫힘 `completed` |
| 폐기 | 닫힘 `not planned`. **사용자만** |
| 원안 보존 · 이력 | 본문은 안 고치고 코멘트를 단다 |
| 정체 | `--search "is:open no:milestone updated:<날짜"` |
| 사이클 | 마일스톤 = 버전 |
| 교차 참조 | `#n` |
| 다른 프로젝트 소관 | `gh issue create -R owner/repo` |
| 미실증 SC | **이슈가 아니다.** `docs/cycles/RISKS.md`(§4.3) |
| 범위 밖 발견 | **close가 이슈를 만들지 않는다.** 결과 절 발견 표. 승격은 비서(§1) |

`init`이 라벨 넷을 만든다. 스킬은 `gh … --json`만 쓴다. 인증은 `gh auth status`가 전부다. GitHub Enterprise는 `gh auth login --hostname`으로 같은 스킬이 돈다. GitHub이 아닌 호스팅은 지원하지 않는다.

### 6.2 브랜치

```
develop ──●────────────●(merge, tag v1.2.0)────●(직접 커밋)──●(merge, tag v1.3.0)──
           \          /                                    /
            v1.2.0-enhance-lyric-sync            v1.3.0-refine-foo
main    ─────────────────────────────●(release: ff → v1.2.0)──────────────────────
```

- `main` 보호. 태그로 `--ff-only`만. release가 배포 시점에만 전진시킨다.
- `develop` 통합. 사이클 머지 커밋과 작은 수정 커밋. 태그는 머지 커밋에.
- `{버전}-{이름}` 작업. 배치마다 `B-n: {이름}` 커밋.
- 브랜치 이름이 다르면 `CLAUDE.md` `## cycle` 절에 적는다.

버전은 start에서 정한다. 사이클은 minor, major는 사용자가 새 시대를 열 때만. 작은 수정만 쌓여 릴리즈할 땐 patch.

### 6.3 README 표준

정본은 `skills/scaffold/readme.standard.md`다. scaffold가 그 골격으로 만들고 close가 사이클마다 대조한다.

골격: 제목 + 한 줄 → 이게 뭔가(3문장) → 설치(명령만) → 사용(핵심 흐름 하나) → 구조(트리, 개수 없음) → 더 보기.

금지: 상태 · 진행 블록, 설치 명령 밖의 버전 번호, 이력("~에서 추가됨", "이번 사이클에서"), 세는 숫자, 설계 근거, FAQ · 트러블슈팅, **다른 정본(SKILL.md · design.md · SPEC.md)의 재진술**. 절반은 grep으로 잡는다. close가 걸린 것을 보여주고 고친다.

README 외 기본 파일(LICENSE · CONTRIBUTING · `.gitignore` · 이슈 템플릿)은 scaffold가 한 번 만들고 다시 건드리지 않는다. CHANGELOG는 만들지 않는다. GitHub Release가 대신한다.

### 6.4 프로젝트별 규칙 — `CLAUDE.md`

스킬 전용 규칙 파일은 없다. 프로젝트별 규칙이 사는 자리는 이미 `CLAUDE.md`이고, 세션마다 자동으로 읽히므로 스킬이 "그 파일을 읽어라"를 기억할 필요도 없다. `init`이 `## cycle` 절 하나를 붙인다.

- 검증 명령 — 이 프로젝트에서 SC에 붙일 수 있는 수단과 명령. `init`이 실측하고 실제로 돌려 본 뒤 문답으로 세운다. 이 절의 핵심이다.
- 브랜치 — `develop` → `main` ff-only가 아닐 때만.
- 종료 훅 — close가 추가로 하는 일(버전 파일 등)이 있을 때만. "README 최신화"는 쓰지 않는다. 표준 대조가 이미 한다.
- 릴리즈 노트 — 제품명이 레포 이름과 다르거나 톤이 "-습니다"가 아닐 때만.

기본값과 같은 줄은 두지 않는다.

## 7. 스킬

| 스킬 | 읽음 | 씀 | 하지 않는 것 |
|---|---|---|---|
| `start` | 인자 이슈, `SPEC.md`, `RISKS.md` 미해소 행, 코드 | 사이클 문서(범위 · 배치), 마일스톤 + 배정, 브랜치, B-1 | 백로그 고르기, 이슈 만들기 |
| `resume` | 범위 절, 미완 배치 행, `git log` | 없음(이어지는 배치가 쓴다) | 문서 전체 읽기, 배치 다시 짜기 |
| `close` | 사이클 문서, diff | 결과 절, `SPEC.md`, `RISKS.md`, README, 태그, 이슈 상태, 마일스톤 설명 | 감사, 릴리즈, 새 이슈, `not planned` |
| `release` | `gh release list`, 태그 간 diff | GitHub Release, `main` 전진 | 사이클 문서, 이슈, 노트 파일 |
| `init` | 저장소, `gh auth status`, 이전 체계 흔적 | 라벨, `CLAUDE.md` `## cycle` 절, `docs/cycles/`, `develop` | 있는 것 덮어쓰기, `CLAUDE.md` 다른 절 수정 |
| `scaffold` | 저장소 | README(표준), LICENSE, CONTRIBUTING, `.gitignore`, 이슈 템플릿 | 있는 파일 덮어쓰기(README는 표준 대조 후 사용자 확인) |

호출은 `/cycle:<스킬>`이다. 배치 루프의 절차는 `skills/start/batch.md` 하나에 있고 start와 resume이 같이 읽는다.
