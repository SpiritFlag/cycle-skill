# cycle-skill 설계

> 이 문서는 cycle-skill이 왜 이렇게 생겼는지를 적는다. 쓰는 법은 `README.md`, 각 단계의 절차는 `skills/*/SKILL.md`가 정본이다. 셋은 서로를 다시 쓰지 않는다.

---

## 0. 왜 다시 세우나

pdca-skill v1을 자기 자신에게 여섯 사이클 돌린 뒤 남은 관찰이다.

1. **이름이 실체와 어긋났다.** 검증을 Do가 맡은 순간 Check가 사라졌고, Act는 report · backlog-sync · 사람 손으로 흩어졌다. 단계를 P · D · C · A 어디에 넣을지 분류하는 일 자체가 비용이 됐다. 실체는 순환이 아니라 **게이트가 있는 단계열**이다.
2. **형식이 내용을 밀어냈다.** 사이클 하나에 문서 여섯, 인덱스 · 리스크 · 릴리즈 폴더, 문서마다 Version History. 스킬 100줄을 고치려고 그보다 긴 문서를 썼다. close의 감사(analysis)는 Do가 이미 검증한 것을 다시 검증했고, 잡아낸 결함은 "README 트리에서 개수를 안 셌다" 수준이었다.
3. **plan과 design의 구분이 실재하지 않았다.** "할까?"는 propose에서 이미 정해지므로 plan에는 실측과 성공 기준만 남고, design은 그것을 다시 쓰며 두꺼워졌다. 사용자가 여러 사이클을 돌려도 둘의 차이를 체감하지 못했다.
4. **도구가 사용자와 싸웠다.** 자체 서버(PDCA-workspace)와 CLI(pdcaw)는 설정 파일 둘, PAT, npm 감사 우회 플래그를 요구했다. 백로그 하나 때문에 유지한 인프라다.
5. **자기 도그푸딩이 구조적으로 막혔다.** 스킬은 플러그인 캐시에서 실행되므로 스킬을 고치는 사이클이 자기 산출물을 실행하지 못한 채 닫혔다. 하루에 패치 여섯이 나왔다.

## 1. 원칙

| # | 원칙 | 뜻 |
|---|---|---|
| P1 | **정본은 git, 백로그는 GitHub Issues.** | 사이클 문서는 레포에 있다. 백로그 · 마일스톤 · 릴리즈는 GitHub이 맡고 스킬은 `gh`로만 만진다. 자체 서버 · 설정 파일 · 토큰 파일은 없다. |
| P2 | **문서는 독자로 정의한다.** | 같은 독자에게 같은 내용을 두 문서에 쓰지 않는다. README도 예외가 아니다. |
| P3 | **검증은 Do가 한다.** | 배치마다 그 배치 범위를 검증하고 do 문서에 기록한다. 전체 검증은 close가 사이클에 한 번 돌린다. close는 감사하지 않는다. |
| P4 | **세션 하나 = 단계 하나.** | 세션은 자기 단계 문서만 쓴다. 이전 단계 문서는 읽기 전용이다. Do만 여러 세션 · 여러 회차에 걸친다. |
| P5 | **의식적 형식 금지.** | 고정 개수 선택지, 합산 수치, 개정마다 자라는 요약, 통과를 선언하기 위한 게이트 표, 감사를 위한 감사를 두지 않는다. 전제조건은 조용히 확인하고 막힐 때만 말한다. |
| P6 | **판단은 사용자.** | 범위 선택, 확정, 폐기는 사용자가 한다. 스킬은 후보와 근거를 내고 멈춘다. |
| P7 | **산출물에서 사용자는 "사용자"다.** | 이름 · 호칭 · 대화체를 쓰지 않는다. 사용자의 말을 원문 그대로 인용하지 않고 감싼다("사용자가 만족했다"). |
| P8 | **README는 사용법까지만.** | 표준 양식이 있고 close가 사이클마다 대조한다. 상태 · 이력 · 버전 · 개수 · 설계 근거는 README에 쓰지 않는다. |

## 2. 흐름

```
propose  →  plan  →  do (회차 N개)  →  close          [배포 결정 시] release
 Opus        Fable     Sonnet          Opus
 scope.md    plan.md   do.md           report.md      GitHub Release
             design.md                 태그
```

단계마다 새 세션을 연다. 모델은 권장일 뿐이고 **스킬이 모델이나 effort를 바꾸지 않는다.** 스킬이 세션 도중 모델을 바꾸면 프롬프트 캐시가 깨져 사용자가 비용과 시간을 문다. 세션을 열 때 사용자가 고른다.

### 2.1 propose

두 단계로 제안한다. 안 셋을 만들어 하나를 고르게 하지 않는다.

1. **고르기.** 열린 이슈를 우선순위 순으로 보여주고 사용자가 이번에 풀고 싶은 것을 고른다.
2. **묶기.** 고른 이슈를 중심으로 같은 접점 · 선후 의존 · 같은 검증 수단으로 묶이는 이슈를 붙여 최종 묶음을 낸다.

그 뒤 **묶음의 항목마다 "구체적으로 무엇을 하는 일인가"를 스킬이 먼저 풀어 쓰고 사용자와 맞춘다.** 이슈 본문은 추상화 · 축약돼 있어 그대로 plan에 넘기면 오해가 난다. 이 합의가 propose의 본체다.

산출물은 `scope.md`와 마일스톤이다. `scope.md`는 plan이 **이 문서만 갖고** 시작할 수 있을 만큼 항목별로 무엇을 · 어떻게 · 왜를 적는다. 어느 이슈에서 왔는지는 부록에 번호로 적는다(close가 닫을 때 쓴다). 마일스톤은 버전 이름으로 만들고 묶음 이슈를 배정한다. 이슈의 `doing` 상태는 마일스톤 배정이 대신한다.

이슈 없이 사용자가 주제를 직접 줘도 같은 절차다. 그때 부록은 "직접 지시"다.

### 2.2 plan

백로그를 보지 않는다. 범위를 묻지 않는다. 근본 결정은 propose에서 합의됐어야 하므로 여기서 물어야 한다면 scope.md가 부족한 것이고, 그 사실을 사용자에게 말하고 propose로 돌려보낸다. 코드 레벨의 결정만 사용자와 맞춘다.

산출물이 둘이다. 독자가 다르다.

| 문서 | 독자 | 성격 |
|---|---|---|
| `plan.md` | 사용자 | 이 사이클이 무엇을 어떻게 바꾸는지 **쉽고 자세하게** 설명한다. 이 언어 · 이 엔진을 모르지만 프로그래밍 기본기가 있는 사람이 따라올 수 있어야 한다. 결정과 근거, 갈림길이 있었으면 선택지와 대가, 리스크. 문서 전체를 가볍게 쓰라는 뜻이 아니라 개념을 풀어 쓰라는 뜻이다 |
| `design.md` | 구현 세션(Sonnet) | 배치(B-n)별 작업 지시서. 파일 · 시그니처 · 순서 · 배치마다 "무엇을 확인하면 끝인가". 설명 없이 지시만. do는 읽기만 한다 |

검수 루프: 초안을 쓰고 경로만 보고하고 멈춘다 → 사용자가 의견을 준다 → 반영한다 → "확정". 확정 전에 do 세션을 열지 않는다.

### 2.3 do

시킨 대로 우직하게 한다. 사용자는 최대한 간섭하지 않는다.

- **문서.** `design.md`가 지시서, `do.md`가 기록이다. do는 `design.md` · `plan.md`를 읽기만 하고 `do.md`만 쓴다. `do.md`는 1회차가 만든다. 지시서와 기록이 한 파일에 있으면 기록이 지시서 틈새로 흘러 들어가 둘 다 읽기 어려워진다.
- **회차.** 사용자가 프롬프트를 한 번 치면 회차가 하나 는다. 종류는 넷 — `착수`(새 배치) · `재시도`("다시해") · `답`(Q-n에 답) · `확인`(육안 결과). 회차마다 do.md에 소절 R-n 하나 — 제목에 종류와 배치, 표 하나(한 일 · 검증 · 문제 · 조치 · 결과), 5줄 상한. 회차에서 벌어진 일은 R-n에만 적는다. 진행 표는 두지 않는다. 지시 칸이 "다음"으로 도배되고 배치 상태 표와 겹쳤다. 배치별 요약은 배치 상태 표, 회차별 상세는 R-n이다.
- **표.** do.md는 표로 쓴다. 배치 상태 · 진행 · R-n · 결정 · 질문 전부. 문장은 표 칸 안에 둔다. 서사가 절 아래에 문단으로 자라는 것을 막는 장치다.
- **배치.** 하나를 구현하고 검증까지 끝내고 기록한 뒤 다음으로 간다. 검증 기록에 없는 것은 검증되지 않은 것이다. 뼈대만 넓게 치지 않는다.
- **검증 범위.** 배치 검증은 그 배치가 건드린 범위만 돈다. plan이 지시서에 좁혀 적는다. 전체 검증 명령을 배치마다 돌리면 배치 수만큼 세션 시간이 새기 때문이다.
- **문서 권한.** do.md는 자유롭게 고친다. plan.md · design.md를 바꿔야 하는 일이 생기면 질문으로 사용자와 협의한다.
- **질문.** 임시 파일을 만들지 않는다. do.md의 질문 절에 질문 · 설명 · 선택지 · 추천을 적고 멈춘다. 답도 그 절에 적는다. do.md 범위 안의 세부는 묻지 않고 정하고 결정 절에 이유를 남긴다.
- **테스트.** 지시서가 지목한 테스트만 고치고 없앤다. 그 밖의 실패 테스트를 통과시키려는 수정은 질문이다. skip · quarantine으로 초록을 만들지 않는다.

`--auto`를 주면 배치마다 서브에이전트를 띄워 메인 세션의 컨텍스트를 아낀다. 기본은 회차 하나에 배치 하나다.

### 2.4 close

전제조건을 **조용히** 확인한다. 질문 절에 답 없는 질문이 없고, 검증 안 된 배치가 없고, 버전 태그가 아직 없으면 시작한다. 막히면 무엇이 막는지 한 줄만 말하고 멈춘다. 통과했다고 보고하지 않는다.

1. `CLAUDE.md` `## cycle` 절의 자동 검증 명령이 있으면 한 번 돌린다. 사이클에서 전체 검증이 도는 유일한 자리다. 결과만 적는다.
2. `report.md`를 쓴다(§3.4).
3. README를 표준과 대조한다(§6).
4. `## cycle` 절의 종료 훅(버전 파일 등)을 실행한다.
5. 사이클 브랜치에 커밋 · 푸시 → 통합 브랜치에 `--no-ff` 머지 → 머지 커밋에 태그 → 푸시 → 사이클 브랜치 삭제(`-d`). **푸시 전에 한 번 묻는다.**
6. 이슈를 정리한다. report 부록을 따라 닫고(`completed`), 이월은 마일스톤을 떼고 코멘트를 남기고, 범위 밖 발견은 새 이슈로. `not planned`는 사용자만 찍는다. 마일스톤을 닫는다.

릴리즈는 만들지 않는다.

### 2.4.1 검증의 자리

검증은 세 겹이 될 수 있다. 각각의 자리를 정한다.

| 겹 | 자리 | 범위 | 스킬의 태도 |
|---|---|---|---|
| 배치 검증 | do, 배치마다 | 그 배치가 건드린 범위 | 돌리고 기록한다 |
| 전체 검증 | close §1, 사이클에 한 번 | `## cycle` 절의 전체 명령 | 머지 전 게이트. 돌리고 기록한다 |
| 원격 CI | GitHub Actions 등, 통합 · 릴리즈 브랜치 푸시 | 프로젝트 설정 | **기다리지 않고 기록하지 않는다.** 안전망이다 |

원격 CI는 통합 · 릴리즈 브랜치 푸시에 걸린 것으로 본다. 사이클 브랜치에도 걸려 있으면 do가 푸시할 때마다 돌게 되므로 init이 빼기를 권한다. 릴리즈 브랜치는 태그로 ff만 하므로 같은 커밋이 다시 검증되지만, 그것은 프로젝트 사정이라 건드리지 않는다.

### 2.5 release

사이클과 무관하게 **배포를 결정했을 때** 부른다.

| 대상 | GitHub Release | 용도 |
|---|---|---|
| `develop` | pre-release | 대내. 보고 · 검수 · 게시 |
| `main` | release | 대외 |

노트는 **직전 같은 종류 릴리즈부터 대상 태그까지의 diff**로 쓴다. 사이클 문서를 모으지 않는다. 사이클 밖에서 커밋한 것도 diff에 있으므로 빠지지 않는다. `main`은 태그로 `--ff-only` 전진한다(룰셋으로 막혀 있으면 `## cycle` 절에 적힌 방식). 릴리즈 노트 파일을 레포에 남기지 않는다. GitHub Release 본문이 정본이다.

### 2.6 작은 수정

패치 트랙은 없다. 설계가 필요 없는 수정은 통합 브랜치에 그냥 커밋한다. 이슈에서 나온 것이면 커밋 메시지에 `closes #n`. 급하면 태그를 찍고 release를 부른다. 설계가 필요하면 그것은 사이클이다.

## 3. 문서

### 3.1 위치

```
docs/cycles/
  v1/
    v1.2.0-enhance-lyric-sync/
      scope.md
      plan.md
      design.md
      do.md
      report.md
```

- 사이클 폴더는 `{버전}-{사이클명}`. 버전이 열쇠고 사이클명은 꼬리표라 겹쳐도 된다.
- 파일 이름은 단계명만. 폴더가 사이클을 말해준다.
- 메이저 폴더 `v{N}`. 코드네임은 폴더에 넣지 않는다.
- 인덱스 파일은 없다. `ls docs/cycles/v*/`가 인덱스다. 한 줄 요약은 마일스톤 설명이 맡는다.
- 브랜치 이름은 폴더 이름과 같다. 통합 브랜치에서 분기하고 close가 머지한 뒤 지운다.

### 3.2 공통 규칙

- 한국어. 사용자는 "사용자". 사용자의 말을 원문 인용하지 않는다(P7).
- 헤더는 표 하나(`사이클 · 버전 · 상태 · 작성 · 갱신`). 값은 교체한다. Version History는 두지 않는다. 최종본이 기준이다.
- 요약 절 · 합산 수치 · 문서 간 마크다운 링크를 두지 않는다. 다른 문서는 `plan §2`처럼, 파일은 경로를 인라인 코드로, 이슈는 `#n`으로 가리킨다.
- 골격을 먼저 만들고 절 하나씩 채운다.

### 3.3 문서별 정의

| 문서 | 쓰는 단계 | 독자 | 답하는 질문 |
|---|---|---|---|
| `scope.md` | propose | plan 세션 | 무엇을 왜 하기로 합의했나. 항목마다 어떻게 할 생각인가. 어느 이슈에서 왔나(부록) |
| `plan.md` | plan | 사용자 | 이 사이클이 무엇을 어떻게 바꾸나. 왜 그렇게 정했나. 무엇이 위험한가 |
| `design.md` | plan | 구현 세션 | 배치별로 무엇을 어떤 순서로 하고 무엇으로 검증하나 |
| `do.md` | do | close | 배치마다 어디까지 됐나. 회차마다 무엇을 했나. 무엇을 정했나. 무엇을 물었고 어떻게 답했나 |
| `report.md` | close | 상급자 | 무슨 문제를 풀려 했고, 무엇을 다뤘고, 어떤 고민에 시간을 썼고, 얼마나 썼고(회차), 무엇이 나왔나 |

### 3.4 report

상급자 보고서다. 코드 레벨 대화는 하지 않는다. 논의한 내용은 추상화하되 가감 없이 보여준다.

1. 배경 — 무슨 문제를 풀려 했나. scope에서.
2. 한 일 — 무엇을 다뤘나. plan의 결정을 사람 말로.
3. 고민 — 어디서 갈림길이 있었고 어떻게 정했나. do의 질문 절과 결정 절에서.
4. 결과 — 성공 기준별로 됐다 · 안 됐다 한 줄. 근거는 do 회차 번호. 쓴 회차 수.
5. 다음 — 다음 사이클에 실제로 바꿀 것 두세 줄. 회고 형식(Keep · Problem · Try)은 없다.
6. 부록 — 이슈 처리표. `닫음 / 이월(사유) / 신규(범위 밖 발견)`, 번호. close가 이 표대로 이슈를 만진다.

## 4. 백로그 = GitHub Issues

| 개념 | GitHub |
|---|---|
| 항목 | 이슈 |
| 우선순위 | 라벨 `p1` `p2` `p3` |
| 대기 | 열림, 마일스톤 없음 |
| 진행 | 열림, 마일스톤 배정 |
| 보류 | 라벨 `hold` + 착수 조건 코멘트 |
| 완료 | 닫힘 `completed` |
| 폐기 | 닫힘 `not planned`. **사용자만** |
| 원안 보존 · 이력 | 본문은 안 고치고 코멘트를 단다 |
| 정체 | `--search "is:open no:milestone updated:<날짜"` |
| 사이클 | 마일스톤 = 버전 |
| 교차 참조 | `#n` |
| 다른 프로젝트 소관 | `gh issue create -R owner/repo` |

`init`이 라벨 넷을 만든다. 스킬은 `gh … --json`만 쓴다. 인증은 `gh auth status`가 전부다. GitHub Enterprise는 `gh auth login --hostname`으로 같은 스킬이 돈다. GitHub이 아닌 호스팅은 지원하지 않는다.

## 5. 브랜치

```
develop ──●────────────●(merge, tag v1.2.0)────●(직접 커밋)──●(merge, tag v1.3.0)──
           \          /                                    /
            v1.2.0-enhance-lyric-sync            v1.3.0-refine-foo
main    ─────────────────────────────●(release: ff → v1.2.0)──────────────────────
```

- `main` 보호. 태그로 `--ff-only`만. release가 배포 시점에만 전진시킨다.
- `develop` 통합. 사이클 머지 커밋과 작은 수정 커밋. 태그는 머지 커밋에.
- `{버전}-{사이클명}` 작업. 문서 · 코드 자유롭게 커밋.
- 브랜치 이름이 다르면 `CLAUDE.md` `## cycle` 절에 적는다.

버전은 propose에서 정한다. 사이클은 minor, major는 사용자가 새 시대를 열 때만. 작은 수정만 쌓여 릴리즈할 땐 patch.

## 6. README 표준

정본은 `skills/scaffold/readme.standard.md`다. scaffold가 그 골격으로 만들고 close가 사이클마다 대조한다.

골격: 제목 + 한 줄 → 이게 뭔가(3문장) → 설치(명령만) → 사용(핵심 흐름 하나) → 구조(트리, 개수 없음) → 더 보기.

금지: 상태 · 진행 블록, 설치 명령 밖의 버전 번호, 이력("~에서 추가됨", "이번 사이클에서"), 세는 숫자, 설계 근거, FAQ · 트러블슈팅, **다른 정본(SKILL.md · design.md)의 재진술**. 절반은 grep으로 잡는다. close가 걸린 것을 보여주고 고친다.

README 외 기본 파일(LICENSE · CONTRIBUTING · `.gitignore` · 이슈 템플릿)은 scaffold가 한 번 만들고 다시 건드리지 않는다. CHANGELOG는 만들지 않는다. GitHub Release가 대신한다.

## 7. 프로젝트별 규칙 — `CLAUDE.md`

스킬 전용 규칙 파일은 없다. 프로젝트별 규칙이 사는 자리는 이미 `CLAUDE.md`이고, 세션마다 자동으로 읽히므로 스킬이 "그 파일을 읽어라"를 기억할 필요도 없다. `init`이 `## cycle` 절 하나를 붙인다.

- 검증 명령 — 이 프로젝트에서 SC에 붙일 수 있는 수단과 명령. `init`이 실측하고 실제로 돌려 본 뒤 문답으로 세운다. 이 절의 핵심이다.
- 브랜치 — `develop` → `main` ff-only가 아닐 때만.
- 종료 훅 — close가 추가로 하는 일(버전 파일 등)이 있을 때만. "README 최신화"는 쓰지 않는다. 표준 대조가 이미 한다.
- 릴리즈 노트 — 제품명이 레포 이름과 다르거나 톤이 "-습니다"가 아닐 때만.

기본값과 같은 줄은 두지 않는다.

## 8. 스킬

| 스킬 | 언제 | 읽음 | 씀 | 하지 않는 것 |
|---|---|---|---|---|
| `init` | 프로젝트를 세울 때, 옮겨올 때 | 저장소, `gh auth status`, 기존 `docs/PDCA/` · pdcaw 백로그(이식) | 라벨, `CLAUDE.md` `## cycle` 절, `docs/cycles/`, `develop` | 있는 것 덮어쓰기, `CLAUDE.md` 다른 절 수정 |
| `scaffold` | init 뒤 한 번 | 저장소 | README(표준), LICENSE, CONTRIBUTING, `.gitignore`, 이슈 템플릿 | 있는 파일 덮어쓰기(README는 표준 대조 후 사용자 확인) |
| `propose` | 다음 사이클을 정할 때 | 열린 이슈, 직전 report §5, 코드 | `scope.md`, 마일스톤 + 이슈 배정, 브랜치 | 이슈 닫기, 코드 수정 |
| `plan` | scope 확정 뒤 | `scope.md`, 코드 | `plan.md`, `design.md` | 이슈 접근, 범위 질문, 코드 수정, `do.md` 생성 |
| `do` | plan 확정 뒤 | `design.md` | 코드, `do.md` | `plan.md` · `design.md` 임의 변경, 검증 없이 다음 배치, 임시 파일 |
| `close` | 전 배치 검증 뒤 | `scope` · `plan` · `do`, diff | `report.md`, README, 태그, 이슈 상태 | 감사 문서, 릴리즈, `not planned` |
| `release` | 배포를 결정했을 때 | `gh release list`, 태그 간 diff | GitHub Release, `main` 전진 | 사이클 문서, 이슈, 노트 파일 |

호출은 `/cycle:<스킬>`이다. `propose`만 인자를 받을 수 있고(직접 지시 문장), 나머지는 현재 브랜치에서 사이클을 읽는다.
