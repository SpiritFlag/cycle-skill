# propose

다음 사이클의 범위를 사용자와 **합의**한다. 안 셋을 만들어 하나를 고르게 하지 않는다. 고르기 → 묶기 → 항목별 합의 → 문서.

> **공통 규칙**
> - GitHub 접근은 `gh … --json`뿐이다.
> - 산출물에서 사용자는 "사용자"다. 사용자의 말을 원문 그대로 인용하지 않는다.
> - 전제조건은 조용히 확인한다. 막힐 때만 한 줄.
> - 이슈를 닫거나 코드를 고치지 않는다.

---

## 0. 전제

`gh auth status` 통과, `CLAUDE.md`에 `## cycle` 절 존재, 작업트리 깨끗함. 절이 없으면 `/cycle:init`을 안내하고 멈춘다.

## 1. 재료

1. 열린 이슈 전건: `gh issue list --state open --limit 200 --json number,title,labels,milestone,updatedAt,body`.
2. 직전 사이클 report: `docs/cycles/` 아래 버전이 가장 높은 폴더의 `report.md` §5(다음). 없으면 건너뛴다.
3. 버전 사다리: `git tag --sort=-v:refname | head`, `gh api repos/{owner}/{repo}/milestones --jq '.[].title'`.
4. 인자로 직접 지시 문장이 왔으면 그것이 재료다. 이슈 목록은 "이미 있는 이슈 중 겹치는 것"을 찾는 용도로만.

## 2. 고르기

마일스톤이 없는 열린 이슈를 **우선순위(p1 → p3) · 갱신일 순** 표로 보여준다. `번호 · 제목 · 라벨 · 마지막 갱신`. `hold`는 따로 묶어 아래에. 30일 넘게 안 움직인 것은 표시한다.

"이번에 풀고 싶은 것을 골라 달라"고 하고 멈춘다. 추천이 있으면 한 줄로 이유와 함께. 직접 지시가 왔으면 이 단계는 건너뛴다.

## 3. 묶기

고른 이슈를 중심으로 다음 기준 중 하나로 설명되는 이슈만 붙인다. "둘 다 급해서"는 기준이 아니다.

- 같은 접점 — 같은 파일 · 모듈 · 스키마 · 씬.
- 선후 의존 — A 없이 B가 안 된다.
- 같은 검증 — 한 번의 실측 · 한 번의 육안으로 같이 검증된다.
- 같은 도입 — 외부 도구 하나에 딸린 준비 · 전환 · 정리.

묶음은 3~5건이 기본. 6건을 넘으면 쪼개자고 한다. 붙인 이슈마다 어느 기준인지 이름으로 적는다. 사용자가 빼거나 더한다.

## 4. 항목별 합의 ★ 이 절차의 본체

이슈 본문은 추상화 · 축약돼 있다. 그대로 넘기면 plan이 오해한다. 그래서 묶음의 **항목마다** 스킬이 먼저 풀어 쓰고 사용자와 맞춘다.

항목마다 코드를 훑어(파일 · 함수 · 현재 동작을 직접 읽는다) 아래를 쓴다.

- **무엇을** — 지금 어떤 상태이고 무엇이 어떻게 달라지나. 구체적으로.
- **어떻게** — 어느 층을 어떤 방향으로 건드릴 생각인가. 코드 수준이 아니라 접근 수준.
- **왜** — 이 방향인 이유. 다른 길이 있으면 왜 아닌지.
- **끝났다는 기준** — 무엇을 보면 됐다고 할 것인가.

한 항목씩 보여주고 사용자 의견을 받아 고친다. 이 왕복이 여러 번이어도 된다. **여기서 합의 안 된 것은 plan에서 범위 질문으로 돌아온다.** 그러면 propose가 덜 된 것이다.

같은 이름의 사이클이 `docs/cycles/*/*-{이름}`에 이미 있으면 그때 무엇을 했는지 한 줄 상기시킨다.

## 5. 이름과 버전

- 사이클명 `<종류>-<대상>`, 케밥. 종류는 `explore`(새 영역) · `adopt`(외부 도입) · `enhance`(기존 개선) · `refine`(정리 · 마감). 둘에 걸치면 지배적인 하나. 못 고르면 응집도가 낮은 것이니 쪼갠다.
- 버전은 최신 태그의 **minor +1**. major는 사용자가 새 시대를 열 때만이라 제안하지 않는다. 마일스톤에 예약된 버전이 있으면 그 다음.
- 이름 · 버전을 보여주고 확인받는다.

## 6. 산출

확인받은 뒤에만.

1. 마일스톤: `gh api repos/{owner}/{repo}/milestones -f title={버전} -f description="{한 줄 목적}"`. 이미 있으면 재사용.
2. 이슈 배정: 묶음의 이슈마다 `gh issue edit {n} --milestone {버전}`.
3. 브랜치: `git switch -c {버전}-{사이클명} {통합 브랜치}`.
4. 폴더 `docs/cycles/v{major}/{버전}-{사이클명}/`와 `scope.md`. `${CLAUDE_SKILL_DIR}/scope.template.md`를 채운다. §4에서 합의한 항목이 본문이고, 이슈 번호는 부록이다. **plan이 이 문서만 갖고 시작할 수 있어야 한다.**
5. 커밋 `scope: {버전}-{사이클명} 열기`, 푸시.

## 7. 보고

두 줄. 사이클 · 버전 · 브랜치, 그리고 "새 세션에서 `/cycle:plan`".

## 하지 않는 것

- 안 2~3개를 만들어 택일시키지 않는다.
- 이슈 닫기 · `not planned` · 본문 수정. 코드 수정.
- 설계 · 파일 목록 · 배치. 그것은 plan이다.
- 합의 안 된 항목을 scope에 넣지 않는다. 빼고 그 사실을 적는다.
