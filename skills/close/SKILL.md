# close

사이클을 닫는다. 감사하지 않는다. Do가 검증한 것을 믿고, 최종 검증 한 번과 보고서, 정리.

> **공통 규칙**
> - GitHub 접근은 `gh … --json`뿐이다.
> - 산출물에서 사용자는 "사용자"다. 사용자의 말을 원문 그대로 인용하지 않는다.
> - 전제조건은 조용히 확인한다. 통과했다고 보고하지 않는다. 막힐 때만 한 줄.

---

## 0. 전제 (조용히)

- 현재 브랜치 `{버전}-{사이클명}`, 폴더에 `scope.md` `plan.md` `do.md`.
- `do.md` §1 전 배치 `검증 완료`. §4에 `열림` 상태 Q-n 없음.
- `git tag`에 `{버전}` 없음. 작업트리 깨끗함.
- 검증 명령 · 브랜치 · 종료 훅은 `CLAUDE.md`의 `## cycle` 절에 있다.

하나라도 아니면 무엇이 막는지 한 줄 말하고 멈춘다.

## 1. 최종 검증

`## cycle` 절의 자동 검증 명령이 있으면 **한 번** 돌린다. 결과(통과 · 실패)만 report §4에 적는다. 실패하면 멈추고 사용자에게 보인다. 고치는 것은 do 회차다.

테스트 파일을 열어 단언 내용을 읽거나 D-n 이행을 대조하지 않는다.

## 2. report.md

`${CLAUDE_SKILL_DIR}/report.template.md`로 골격을 만들고 절 하나씩 채운다.

**독자는 상급자다.** 코드 레벨의 대화는 하지 않는다. 논의한 내용은 추상화하되 **가감 없이** 보여준다. 잘 안 된 것, 돌아간 길, 다시 한 회차도 그대로.

- §1 배경 — scope §1에서. 무슨 문제를 왜 풀려 했나.
- §2 한 일 — plan §1 · §2를 사람 말로. 무엇이 어떻게 달라졌나.
- §3 고민 — do §3 결정 · §4 질문에서. 어디서 갈림길이 있었고 어떻게 정했나. 사용자의 결정은 감싸서.
- §4 결과 — SC마다 됐다 · 안 됐다 한 줄, 근거는 do 회차 번호. 쓴 회차 수와 배치별 회차. §1의 최종 검증 결과.
- §5 다음 — 다음 사이클에 실제로 바꿀 것 두세 줄. 회고 형식(Keep · Problem · Try)은 쓰지 않는다.
- 부록 — 이슈 처리표. scope 부록의 이슈마다 `닫음 / 이월(사유) / 신규(범위 밖 발견)`. do §3 · §4에서 나온 범위 밖 발견은 신규 행. **부분 해결은 닫음이 아니다.** 이월로 두고 무엇이 남았는지.

## 3. README 대조

`skills/scaffold/readme.standard.md`(플러그인 루트 기준 `${CLAUDE_SKILL_DIR}/../scaffold/readme.standard.md`)를 읽고 그 절차대로. 이번 사이클 diff에서 README에 반영할 것을 반영하고, 기계 대조 · 사람 대조를 돌린다. 걸린 것은 고치고, 갈리면 사용자에게. 결과 한 줄을 §6 보고에.

## 4. 종료 훅

`## cycle` 절의 종료 훅을 순서대로. 없으면 건너뛴다.

## 5. 커밋 · 머지 · 태그

1. `do.md` 헤더 상태를 `완료`로. 사이클 브랜치에 커밋 `close: {버전}-{사이클명}`, 푸시.
2. **사용자에게 한 번 묻는다** — 통합 브랜치에 머지하고, 태그를 밀고, 사이클 브랜치를 지워도 되는지.
3. `git switch {통합}` → `git merge --no-ff {사이클 브랜치} -m "merge: {버전}-{사이클명}"` → `git tag -a {버전} -m "{사이클명} — {한 줄}"` → `git push --follow-tags`.
4. `git rev-parse {버전}^{}`가 머지 커밋인지 확인한다.
5. 사이클 브랜치를 지운다. `git branch -d {사이클 브랜치}` → `git push origin --delete {사이클 브랜치}`.
   `-d`는 머지되지 않은 브랜치를 거부하므로 4의 확인이 실패한 경우 여기서도 막힌다. `-D`를 쓰지 않는다.
   거부되면 지우지 말고 무엇이 머지되지 않았는지 한 줄 보고한다.

릴리즈 브랜치는 건드리지 않는다. 릴리즈도 만들지 않는다.

## 6. 이슈 정리

report 부록대로.

| 행 | 명령 |
|---|---|
| 닫음 | `gh issue close {n} -r completed -c "{버전}에서 처리. {한 줄 근거}"` |
| 이월 | `gh issue edit {n} --remove-milestone` + `gh issue comment {n} -b "{버전}에서 이월. 남은 것: {…}"` |
| 보류 | 이월과 같되 `--add-label hold`, 코멘트에 착수 조건 |
| 신규 | `gh issue create -t "{제목}" -b "{무엇이 · 끝나는 기준 · 출처: {버전} do §n}" -l p2` |
| 폐기 후보 | **닫지 않는다.** 코멘트로 "폐기 후보 — {이유}"만 남기고 사용자에게 번호를 알린다 |

마일스톤에 열린 이슈가 남아 있지 않으면 닫는다: `gh api -X PATCH repos/{owner}/{repo}/milestones/{number} -f state=closed`. 남아 있으면 그 번호를 사용자에게 보이고 묻는다.

## 7. 보고

- 버전 · 사이클명 · 태그 커밋 한 줄.
- 이슈 처리 요약(닫음 n · 이월 n · 신규 n). README 대조 결과 한 줄.
- 사용자가 정할 것(폐기 후보 · 마일스톤에 남은 이슈)이 있으면 번호로.
- 배포하려면 `/cycle:release develop` 또는 `main`.

## 하지 않는 것

- 감사 문서. 게이트 통과 표. 합산 수치.
- 릴리즈 생성. 릴리즈 브랜치 전진.
- `not planned`. 부분 해결 닫기.
- 사용자 확인 없이 머지 · 태그 푸시.
- README에 이번 사이클 이력 쓰기.
